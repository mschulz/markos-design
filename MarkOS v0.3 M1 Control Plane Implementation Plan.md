# MarkOS v0.3 M1 Control Plane Implementation Plan

## Proposed outcome and authority

Build an authenticated shared interaction gateway over the independent runtime: a user can inspect scoped agent health/activity, exchange durable messages with a deterministic test agent, review versioned configuration and decide exact synthetic approval requests through the same web and CLI API. Implement registry/policy/approval/audit contracts and a governed synthetic read-only MCP path. Deliver each slice through a separate reviewed PR. This document authorizes no implementation, merge, account connection, provisioning or deployment; it is the concrete proposal for the next milestone.

Follow [[ADR-004 Event-driven Architecture Supersedes Legacy MarkOS]], [[MarkOS v0.3 Specification]] and [[ADR-005 Governed MCP Access for Agents]]. RabbitMQ remains the internal bus; PostgreSQL owns operational state, conversations and audit; source originals remain object references and Markdown remains a derived export. No PARA, Obsidian, archived `markos` dependency or MacBook service is introduced. Preserve the rules-first M3 classifier design: M1 supplies identity/registry/configuration, without choosing Jev or an LLM. Native Gmail/Pub/Sub remains an independent M2 path.

## Identity, permissions and session decisions proposed

Use an identity-provider adapter; recommend Supabase Auth as the first production candidate because the hosting baseline already uses Supabase, subject to an M1-A ADR. M1 implementation acceptance uses a local signed-token/PKCE-compatible issuer fixture with no real account. Verify signature against configured trusted keys, explicit issuer/audience/algorithm, token type, expiry/not-before and required subject/session claims. Never trust decoded claims without verification, choose a key URL from an untrusted token, silently accept another issuer or fall back to an anonymous principal. Bound key fetching/cache lifetime, key rotation and authentication errors. A valid signature is not proof that a session is still authorized.

Map `(issuer, subject)` to administratively provisioned owner/domain memberships and roles in PostgreSQL. Proposed roles: viewer (scoped summaries), operator (chat and permitted controls), approver (exact intents), administrator (reviewed registry/configuration). No role can approve outside its membership, turn a denied tool into an allowed one or grant itself a domain. Agents are distinct service principals and cannot impersonate humans or approve their own requests. Revocation checks are database-backed at each request/dispatch; authentication/session/policy lookup failure closes protected operations. Federation-wide revocation semantics and production login method must be settled in M1-A; test local session revocation immediately, and do not claim offline JWT verification provides immediate provider logout.

Use same-origin server-managed browser sessions: random opaque identifiers, hashed session lookup, encrypted refresh material if needed, Secure/HttpOnly/SameSite cookies, session rotation at login, explicit expiry/logout and CSRF plus Origin checks on writes. Provider tokens never enter browser storage or URLs. The proposed initial session ceilings are 30-minute idle and eight-hour absolute, bounded further by token/provider policy; these need owner review. CLI receives a short-lived scoped bearer via an explicit PKCE/browser onboarding flow, never a committed token or command-line argument. Tests use fixtures only. Define provider token renewal and local session revocation together before claiming login complete.

The gateway is a trusted delegation service, not a transparent browser database connection. Give its dedicated non-admin/non-BYPASSRLS login EXECUTE only on narrow control-plane functions; no base-table writes, migration privileges, broker administration or service-role secrets. It supplies the verified actor, and every database function checks current actor membership, object scope, role and version. This explicitly trusts gateway authentication to bind the actor: PostgreSQL does not magically recover a human JWT from the existing service login. Never use an arbitrary `SET owner_id`, pooled connection state or a browser-provided actor as authority. Separate publisher/worker identities from gateway read/write authority; test pool reuse across owners/domains and function grants directly. Record this boundary and its compromise implications in the M1-A ADR.

## Durable chat, configuration and approvals

A new human request creates conversation/message identity, idempotency record, activity and a typed `control.chat.requested` event plus intended consumer/outbox in one transaction. The chat variant carries a typed scoped message reference, not M0’s cloud `SourceReference`, conversation text, credentials or an approval token. Freeze routes `v1.control.chat-requested` to logical consumer `control-test-agent` and `v1.control.chat-completed` for the versioned `control.chat.completed` result reference to `control-activity`. The latter performs only durable scoped activity handoff; it is not a new agent executor. Exact consumer intent, producer identities, permissions and bindings are reviewed with the contracts. API returns **202 plus durable IDs**, not a promise of completion; it does not hold a broker delivery or request open while an agent runs. Repeated identical actor/scope/operation keys return the same result; changed content under the same key returns 409. Use database-serialized sequence numbers per conversation; timestamps alone do not define ordering. Scope reads before pagination/counts/search.

Publisher → RabbitMQ → durable task handoff retains the M0 contract. A fixed `control-test-agent` reads only its authorized synthetic message reference. Initially it returns a bounded deterministic reply without a model, filesystem, shell, provider or private source. A new type-specific database completion function atomically commits assistant message, result, activity and required completion outbox state only with current epoch/fence, run identity and agent/config version. Extend exact routing/consumer-intent/topology validation for the new type; preserve no-op behavior through upgrade/old-wire tests. Do not add arbitrary event types, output JSON or a generic executable plugin registry. Existing M0 schedules remain no-op-only in M1.

Registry stores immutable versioned agent manifests separately from provisioned service identities. Registration does not enable an agent, grant tools or create queues. State is registered/disabled → explicitly enabled; health is fresh/degraded/stale/unknown, separate from enabled status. Compute health from scoped heartbeats with database time, not MacBook polling or a global admin endpoint. Disable blocks new admission/dispatch and records an audit transition; already-issued external outcomes would require reconciliation. Any configuration update validates typed allowlists and uses an expected revision/ETag (409 on stale write); versions, actor, reason and hashes remain in history. Secrets are write-only references and never resolved into configuration responses. No free-form SQL, shell, endpoint, routing-key, environment or executable editor is exposed.

Approval lifecycle is durable: requested → awaiting decision → approved/rejected/expired/revoked, with **one-time consumption at dispatch**, not at the Approve click. Bind owner/domain/human, run/task, exact canonical arguments/preview digest, source/destination/effect, tool/schema, agent/grant/config versions, budget, expiry and operation ID. Approval never overrides a denied grant. Changes invalidate the old intent. Waiting releases execution slots and holds no broker delivery, transaction or live waiter. Resume must claim fresh authority and revalidate all bindings before atomically consuming approval plus writing dispatch audit. Unknown outcomes remain unresolved; no blind retry or automatic restored approval resurrection.

Keep M0 poison/replay reviews distinguishable from human effect approvals. A shared inbox can show typed records with their own authorized actions; “resolve review” cannot imply “approve effect.” M1 exercises decisions using synthetic intents and an ephemeral fixture effect ledger only. Real consequential tools remain disabled.

## Minimal authenticated API and interface

Proposed API prefix `/api/v1`, with stable typed errors, request/correlation IDs and bounded opaque cursors. `/live` is process-only; detailed `/ready`/metrics stay private. Public protected status must redact hostnames, credentials, payloads and unrelated scopes. An unauthorized object lookup returns a consistent 404; missing/invalid authentication returns 401, forbidden capability 403, stale revision/idempotency conflict 409, oversize 413 and admission exhaustion 429. Return retry guidance only where safe.

| Routes / screen | Contract |
|---|---|
| `GET /me`, `POST /session/logout` | Verified memberships/capabilities and local revocation; no self-provisioning or arbitrary owner switch. |
| `GET /agents`, `GET /agents/{id}`, `GET /status` | Scoped version, enabled state, fresh/degraded/stale/unknown health and summarized recent work. |
| `POST /agents`, `POST /agents/{id}/revisions`, `POST /agents/{id}/state` | Administrator preview/validation and expected-version guarded activation/disable with audit; no implicit permission expansion. |
| `GET/POST /conversations`, `GET /conversations/{id}/messages`, `POST /conversations/{id}/messages` | Explicit authorized domain and enabled test agent, idempotent durable admission, persisted replies and ordered pagination. |
| `GET /activity`, `GET /activity/stream` | Persisted scoped activity; resumable SSE cursor, safe reconnect/expired-cursor resync and polling fallback. No direct browser RabbitMQ subscription. |
| `GET /configuration`, `POST /configuration/revisions` | Typed scope-filtered values and redacted secret references; expected revision, validation, audit and preview. |
| `GET /approvals`, `GET /approvals/{id}`, `POST /approvals/{id}/decisions` | Accessible exact preview, approver capability, CSRF/idempotency/version/expiry checks; decision never dispatches directly from an HTTP handler. |

The first interface has Conversations, Agents/Health, Activity, Approvals and Configuration pages; domain selection is always visible and restricted to membership. Use escaped plain text for chat/results, keyboard-operable controls and clear queued/working/awaiting-decision/failed/unknown states. New-user, empty, expired-session and dependency-outage screens must work. No rich Markdown rendering, offline private-content cache, push integration or full PWA service worker is required for this milestone. CLI uses these same routes and decision previews; it cannot open a privileged alternate path.

Proposed test starting bounds: 64-KiB HTTP body, 16-KiB UTF-8 chat text, 256-KiB JSON response, at most 100 list rows, 8-KiB SSE frame, one stream per session/four per principal/20 globally and ten-minute maximum connection. Reauthorize each stream poll (at most 15 seconds) and close on expiry/revocation; no SQL connection/transaction remains held across an idle stream. Bound write admission at 30/minute per principal (burst five), 100 pending chat runs globally and ten per owner/domain, atomically across replicas. Propose at most ten active sessions per principal/100 globally, 100 pending approval intents globally/ten per owner/domain and 100 unresolved-or-reserved dispatch records globally/20 per owner/domain. Reserve unresolved-outcome capacity atomically before a tool attempt, release it only on terminal resolution, and refuse further dispatch when full. Freeze these storage/admission bounds before enabling those paths; reject new admissions with an audited outcome, never evict accepted work. M1-A must freeze these values and exact-byte/one-over tests, plus database pagination/lock/statement deadlines. Gateway 256-MiB/0.5-CPU and pool maximum four are initial synthetic test proposals, separate from ADR-005's aggregate tool gateway budget; shared-VM measurement remains open. Per-process counters cannot enforce global limits.
